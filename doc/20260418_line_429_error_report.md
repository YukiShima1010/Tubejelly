# LINE API 429 エラー調査・修正レポート

- 作成日: 2026-04-18
- 対象: TubeJelly LINE Webhook
- 対象ファイル: `src/line/webhook.ts`

## 1. 事象

以下のログが発生し、LINE 経由のダウンロード処理時にエラーが連鎖していました。

- `LINE APIエラー (429): {"message":"You have reached your monthly limit."}`
- `未処理のPromise拒否`

## 2. 原因分析

### 2-1. 一次原因（外部要因）

LINE Messaging API 側の利用上限（月間上限）に到達しており、メッセージ送信 API が `429` を返却していました。

### 2-2. 二次原因（実装要因）

`429` 発生後のエラーハンドリングで、失敗通知の `pushText` も同様に `429` になり、
その例外が十分に吸収されず `未処理のPromise拒否` として露出していました。

また、Webhook のイベント処理中に送信エラーが throw されると、
リクエスト全体が `500` 応答となる可能性があり、リトライ誘発によるノイズ増大リスクがありました。

## 3. 修正方針

1. LINE API エラーを構造化し、`429` を明確に識別可能にする。
2. 通知送信失敗時に例外を再伝播させず、安全に吸収する経路を用意する。
3. Webhook ではイベント単位で例外を処理し、単一イベント失敗で全体 `500` にしない。

## 4. 実施内容

### 4-1. `LineApiError` を追加

- `statusCode` と `responseText` を保持する専用エラーを追加。
- `LineMessenger.request` で非 2xx 時に `LineApiError` を throw するよう変更。

### 4-2. `safePushText` を追加

- `pushText` をラップする安全関数を追加。
- `429` の場合は警告ログのみ出して通知をスキップ。
- それ以外の送信失敗もログ化し、未処理例外化を防止。

### 4-3. 非同期 catch 内の通知送信を安全化

- コマンド実行失敗通知
- ダウンロード失敗通知
- ダウンロード進捗通知（開始/更新）

上記を `safePushText` 経由に変更。

### 4-4. Webhook イベント処理をイベント単位で保護

- `for (const event of events)` 内で `try/catch` を実施。
- `429` は警告として扱い、他イベント処理を継続。
- 単一イベントの失敗で全体 `500` を返さない構造に改善。

## 5. 修正結果

- `pnpm -s typecheck`: 成功
- `pnpm -s lint -- src/line/webhook.ts`: 成功

## 6. 残課題・運用上の注意

今回のコード修正は「障害の連鎖防止」と「ログ健全化」が目的であり、
LINE 側の月間上限超過そのものは解消しません。

根本対応としては、以下のいずれかが必要です。

1. LINE Messaging API のプラン/上限見直し
2. 月間送信数の抑制（進捗通知の間引き、冗長通知の削減）
3. 通知先チャネルの分散や運用設計の再検討
